## Цель и процесс

Avito-Kitchen — учебный backend-проект для освоения проектирования, разработки, интеграции и эксплуатации реальных программных систем.

Целевой пользовательский сценарий:

**Публичный каталог → аккаунт покупателя → выбор филиала → корзина → checkout → Restaurant принимает заказ → история и статусы.**

После реализации полноценного HTTP-приложения планируется изучение Kafka, разработка веб-интерфейса и развитие DevOps-инфраструктуры.

Работа организована по функциональным блокам:

1. Анализ требований и бизнес-инвариантов.
2. Обсуждение и согласование архитектуры.
3. Подготовка технического задания Codex.
4. Реализация в отдельной Git-ветке.
5. Commit и push.
6. Code review через GitHub.
7. Исправление обнаруженных проблем.
8. Тестирование и верификация.
9. Pull Request и merge после согласования.

Небольшие задачи могут выполняться с ограниченным набором проверок. После завершения функционального блока необходимо проверить накопленные изменения, актуализировать устаревшие тесты и устранить выявленные регрессии.

Реализованный код не считается автоматически протестированным.

Источники истины:

- `docs/product/REQUIREMENTS.md` — согласованные бизнес-правила.
- `docs/product/BACKLOG.md` — открытые задачи, замечания и идеи.
- `AGENTS.md` — правила работы Codex.
- GitHub — актуальный код, история изменений и Pull Requests.
- ADR — существенные архитектурные решения при необходимости.

## Этап 1 — backend в соответствии с бизнес-правилами

### 1.1. Ресторан и каталог

**Статус: реализовано, финальная верификация выполняется.**

Реализованы:

- Общее меню ресторана.
- Создание, изменение и логическая деактивация филиалов и товаров.

- Постоянное хранение редактируемых метаданных ресторана и меню.
- Единая `catalog_revision`.
- Увеличение ревизии при изменении итогового состояния каталога.
- Защита конкурентных изменений через `SELECT FOR UPDATE`.
- Корректная транзакционная граница UnitOfWork и rollback-only.
- Сохранение исторических сущностей без физического удаления.

Связанные PR: #3, #4, #5.

### 1.2. HTTP-синхронизация каталога

**Статус: реализовано, финальная верификация выполняется.**

Реализованы:

- Контракт Full Snapshot Sync v3.
- `catalog_revision` как единственный источник порядка бизнес-состояний.
- Формирование согласованного snapshot в `REPEATABLE READ`.
- SHA-256 checksum канонического содержимого.
- Проверка повторных, устаревших и конфликтующих snapshot.
- Атомарное применение полного состояния каталога в Kitchen.
- Поддержка пропуска ревизий при полном snapshot.
- История `snapshot_id` с ревизиями и checksum.
- Очистка истории старше 30 дней при последующей синхронизации соответствующего ресторана.
- Бессрочное сохранение текущей ревизии и checksum.
- Миграционная совместимость legacy-записей.

Связанный PR: #6.

Ограничения текущей реализации:

- Частичная синхронизация (delta) ещё не реализована.
- Автоматическая повторная HTTP-доставка не реализована.
- Независимой периодической очистки истории нет.
- `branch_version` больше не входит в контракт v3, но сохраняется в существующей БД.
- Фактическая корректность новых миграций и синхронизации должна быть подтверждена проверками.

### 1.5. Корзины

**Статус: базовая реализация существует, необходима доработка.**

Требуется:

- Одна корзина на пару покупатель + филиал.
- Привязка корзины к аутентифицированному пользователю.
- `SELECT FOR UPDATE` и `cart_version`.
- Защита от одновременного изменения.
- Актуализация цен и доступности товаров.
- Подтверждение покупателем новых условий.
- Логическая блокировка корзины при `pending` (вариант A).

Вариант B с разрешёнными изменениями во время `pending` отложен.

### 1.6. Оформление заказов и восстановление после ошибок

**Статус: базовая реализация существует, необходима доработка.**

Требуется:

- Состояния `pending`, успешного оформления и отказа.
- Корректная обработка неизвестного результата после timeout.
- Защита от конкурентного checkout.
- Сохранение исторических цен и данных заказа.
- Правильное управление состоянием корзины.
- Python-worker для восстановления заказов с неопределённым результатом.
- Семь долговечных повторов с backoff/jitter.
- PostgreSQL lease и безопасная конкурентная обработка.
- `needs_attention` и защищённое ручное возобновление.

### 1.7. Жизненный цикл и история заказов

**Статус: запланировано.**

Restaurant управляет переходами:

`accepted → preparing → ready → completed`

Требуется:

- Строгая проверка переходов.
- `status_version`.
- История изменений статусов.
- Локальное представление заказа в Kitchen.

- Transactional Outbox и worker доставки.
- Повторные попытки и идемпотентный приём.
- Восстановление согласованности при сбоях.

Отмена заказа в первой версии не поддерживается.

## Этап 3 — Kafka и частичная синхронизация

**Статус: запланировано после HTTP baseline.**

Порядок внедрения:

1. События изменений каталога.
2. События изменения статусов заказов.
3. Команды создания заказов.

Необходимо изучить и реализовать:

- Topics, partitions, offsets, consumer groups.
- Порядок событий по ключу.
- At-least-once delivery.
- Идемпотентность потребителей.
- Transactional Outbox и при необходимости Inbox.
- Retry/backoff.
- DLQ.
- Версионирование схем и AsyncAPI.
- Диагностику задержек и ошибок.

Для каталога одна успешная транзакция с фактическими изменениями порождает одно логическое delta-событие с `catalog_revision`.

Delta применяется только при:

`incoming_revision = current_revision + 1`

При пропуске событий требуется восстановление через полный snapshot. Full Snapshot Sync продолжает использоваться как механизм первоначальной загрузки и восстановления.

Клиентские запросы к Kitchen остаются HTTP/REST.

**Критерий готовности:** корректная обработка дубликатов, пропусков, рестартов и временных ошибок доставки.

## Статусы и Definition of Done

Основные статусы:

`Idea → Needs discussion → Ready → In progress → In review → Verification → Done`

Дополнительные: `Deferred`, `Blocked`.

Различать:

- **Реализовано** — код внесён.
- **Проверено статически** — выполнено code review.
- **Проверено исполнением** — успешно выполнены соответствующие тесты и проверки.
- **Заблокировано** — дальнейшее выполнение ограничено установленной проблемой.
- **Done** — выполнены все применимые критерии готовности.

Merge PR не заменяет тестирование.

Definition of Done включает:

- Соответствие согласованным требованиям.
- Соблюдение бизнес-инвариантов.
- Поддерживаемую архитектуру.
- Необходимые тесты и проверки.
- Безопасную проверку миграций.
- Отсутствие неустранённых критических замечаний.
- Актуализацию документации при необходимости.
- Фиксацию результатов в Git.
