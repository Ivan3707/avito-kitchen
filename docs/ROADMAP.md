## Цель и процесс

Получить учебный продукт: публичный каталог → аккаунт покупателя → корзины по филиалам → checkout → Restaurant принимает заказ → история и статусы. Затем освоить Kafka, фронтенд, инструменты инженера и отдельно развёртывание/DevOps.

Работаем **вертикальными бизнес-сценариями**, а не отдельными слоями без продукта: требования → инварианты → модели БД/миграции → Repository/UoW → Service → API → тесты → Codex commit/push в ветку → наше ревью по блокам → доработка → верификация → merge по согласованию.

Источники: `docs/product/REQUIREMENTS.md` — утверждённые правила, `docs/product/BACKLOG.md` — открытые задачи и идеи; архитектурные решения — ADR по мере необходимости. `HANDOFF.md` не используется.

## Этап 1 — backend в соответствии с бизнес-правилами

1. **Ресторан и каталог.** Общее меню на ресторан, `MenuItem.is_active`; цены и `BranchMenuItem.is_available` для каждого филиала; soft delete, constraints, безопасные миграции.
2. **Синхронизация.** `catalog_revision` вместо старой модели `generated_at`/`branch_version` как источника порядка; full snapshot, идемпотентный retry, защита конкурентных изменений, восстановление пропусков. SHA-256 канонического состояния для контроля равных ревизий; хранить историю `snapshot_id` 30 дней, текущую ревизию и checksum — постоянно.
3. **Аккаунт и доступ.** Email/password, подтверждение email через Mailpit, восстановление пароля, JWT access 15 минут + непрозрачный refresh 14 дней с ротацией и сессиями, RBAC, защищённый административный API Demo Restaurant и отдельная межсервисная аутентификация.
4. **Корзины.** Одна на пару покупатель+филиал, `SELECT FOR UPDATE` + `cart_version`, реакция на изменения цены и доступности, подтверждение обновлённых условий; при `pending` применяется логическая блокировка изменений (вариант A). Более гибкий вариант B отложен в IDEA-016.
5. **Оформление и история.** Идемпотентность `order_id`, `pending`/успех/отказ/timeout, сохранение всех отказов, корректная очистка/блокировка корзины и история заказов. При неизвестном результате отдельный Python-worker восстанавливает заказ с долговечными retry в PostgreSQL (7 повторов с backoff/jitter, lease, `needs_attention` и защищённое ручное возобновление).
6. **Жизненный цикл.** Restaurant управляет строго последовательными переходами `accepted → preparing → ready → completed`, версиями `status_version` и историей; Kitchen показывает покупателю локальное представление статуса. До Kafka статусы отправляются через HTTP Webhook + Transactional Outbox (с повторной доставкой и идемпотентным приёмом); отмена пока не поддерживается.
7. **Качество контрактов.** OpenAPI, API-ошибки, миграции, unit/contract/DB-тесты, ревью, проверка на регрессии.

**Готовность:** подтверждённые HTTP-сценарии end-to-end и правила согласуются с моделями и API.

## Этап 2 — воспроизводимый HTTP baseline

Изолированный Docker Compose + отдельные PostgreSQL; миграции на пустых и наполненных тестовых БД; проверки каталога, регистрации, корзины, checkout, повторов, отказов и восстановления после timeout; зафиксированная версия для сравнения с Kafka.

**Готовность:** воспроизводимая сборка и проверенная критическая функциональность без обращения к рабочим данным.

## Этап 3 — Kafka и частичная синхронизация

- Сперва выбрать **конкретные** сообщения и границы HTTP/Kafka. Синхронные запросы клиента к Kitchen остаются HTTP.
- Изучить topic/partition/offset/consumer group, порядок по ключу, at-least-once и идемпотентность.
- **Порядок внедрения:** сначала события изменений каталога, затем изменения статусов заказов; после проверки этих потоков — команды создания заказов. Браузер продолжает взаимодействовать с Kitchen по HTTP/REST.
- Изменение каталога — **одно логическое delta-событие на успешную транзакцию**, с `catalog_revision`. Применять только следующий номер; при пропуске ревизии не применять последующие delta до восстановления полным snapshot. Полный snapshot может перескакивать через ревизии.
- Producer: Transactional Outbox в исходной БД; consumer: идемпотентная обработка по `event_id`/версии, при необходимости Inbox в одной транзакции с изменением данных.
- Временные ошибки: retry/backoff; неисправимые сообщения: DLQ с контролируемым повторным запуском. DLQ не позволяет молча проигнорировать пропущенную ревизию каталога.
- Спроектировать topics, partition keys, event schemas, consumer groups, порядок и коммиты offset, schema evolution/AsyncAPI и сценарии отказов перед реализацией; не выбирать параметры преждевременно.
- Сравнить Kafka с рабочей HTTP-интеграцией. При переходе создания заказа на Kafka сохранять `pending` до достоверного ответа Restaurant, неизменный `order_id`/payload и защиту от повторов.

**Готовность:** дубликаты и рестарты обрабатываются безопасно; состояние можно восстановить после пропусков и сбоев.

## Этап 4 — веб-приложение

Отдельный клиент (предварительно React/TypeScript/Vite): публичный каталог, регистрация/вход, меню и цены филиала, корзина, подтверждение изменённых условий, оформление, история и статусы. **Веб-панель Restaurant не входит в план** — для учебных изменений данных используется защищённый административный API.

**Готовность:** основные пользовательские сценарии работают из браузера и проходят проверки ошибок/авторизации.

## Статусы и Definition of Done

`Idea → Needs discussion → Ready → In progress → In review → Verification → Done` (или `Deferred`). Каждый статус опирается на артефакты: согласованные требования, исходники, commit SHA, тесты, миграции и ревью. `Done` допустим только после выполнения применимого DoD, а не по одному отчёту Codex.
