## 1. Цель проекта

Avito-Kitchen — учебный программный проект для освоения проектирования, разработки, интеграции и эксплуатации реальных программных систем.

Основные цели:

- Проектирование архитектуры backend-приложений.
- Анализ бизнес-требований и моделирование предметной области.
- Разработка API, бизнес-логики и межсервисных интеграций.
- Работа с транзакциями, конкурентностью и согласованностью данных.
- Освоение событийной архитектуры и асинхронного взаимодействия.
- Разработка клиентского веб-приложения.
- Освоение инженерных практик и DevOps.
- Профессиональное использование AI-агентов при разработке программных систем.

Целевой пользовательский сценарий:

**Публичный каталог → аккаунт покупателя → выбор филиала → корзина → checkout → принятие заказа рестораном → история и статусы заказов.**

Развитие проекта осуществляется последовательно: архитектурная основа → полноценный HTTP backend → HTTP baseline → Kafka → веб-приложение → итоговая верификация.

Инженерные практики и DevOps развиваются параллельно с основной функциональностью.

### Этап 2 — архитектурный рефакторинг

**Статус: архитектура согласована, реализация предстоит.**

Цель этапа — повысить модульность, поддерживаемость, тестируемость и качество организации бизнес-логики обоих backend-сервисов.

#### 2.1. Структурный рефакторинг

- Организация репозитория в формате Monorepo.
- Переход каждого сервиса на Modular Monolith.
- Feature-first организация исходного кода.
- Разделение ответственности внутри бизнес-модулей.
- Декомпозиция существующих бизнес-сервисов.
- Явное владение бизнес-данными.
- Контролируемое межмодульное взаимодействие.
- Централизованная техническая инфраструктура внутри сервисов.
- Группированный Unit of Work.
- Ручной Dependency Injection и FastAPI Depends.
- Унификация управления долгоживущими ресурсами через lifespan.
- Организация тестов по бизнес-модулям и pytest markers.

#### 2.2. Доменный рефакторинг

Выборочное применение стратегических и тактических принципов Domain-Driven Design:

- Bounded Context и Ubiquitous Language.
- Агрегаты Cart, Order и RestaurantOrder.
- Aggregate Root.
- Rich Domain Model.
- Repository per Aggregate.
- Объединённые Domain и ORM Models.
- Выделение Application Services, Domain Services и Domain Policies при необходимости.
- Защита существующих бизнес-инвариантов.

#### 2.3. Изоляция внешних зависимостей

- Выборочное применение Hexagonal Architecture.
- Ports and Adapters.
- Dependency Inversion.
- Python Protocol для значимых внешних зависимостей.
- Отделение бизнес-контрактов от транспортных реализаций.
- Централизованные HTTP-адаптеры.
- Сборка зависимостей через Composition Root.

#### 2.4. Верификация архитектурных изменений

- Последовательное code review по логическим блокам.
- Проверка соблюдения границ бизнес-модулей.
- Проверка бизнес-инвариантов.
- Проверка транзакционных гарантий.
- Регрессионное тестирование.
- Проверка ORM relationships и сохранения агрегатов.
- Проверка совместимости HTTP-контрактов.
- Проверка миграционной совместимости.
- Ruff и применимые статические проверки.

Проверки выполняются по мере завершения отдельных задач, а не только в конце всего рефакторинга.

#### Ограничения этапа

В рамках архитектурного рефакторинга необходимо сохранить:

- Согласованную бизнес-логику.
- Существующие HTTP-контракты.

Структурный и доменный рефакторинг выполняются отдельными логическими этапами.

## 7. Процесс разработки

Работа организуется по согласованным функциональным и архитектурным блокам.

1. Анализ задачи, требований и бизнес-инвариантов.
2. Обсуждение архитектуры и технических решений.
3. Согласование требований и критериев готовности.
4. Подготовка технического задания Codex.
5. Реализация и выполнение применимых проверок.
6. Commit и push в согласованную Git-ветку.
7. Code review через GitHub по логическим блокам.
8. Формирование и согласование замечаний.
9. Доработка и повторная верификация.
10. Pull Request и merge после согласования результата.

Задачи должны иметь определённые границы ответственности, ожидаемый результат и критерии приёмки.

Не следует объединять независимые архитектурные изменения, новые бизнес-требования и исправления дефектов без обоснованной необходимости.

Обнаруженные во время реализации проблемы фиксируются и обсуждаются отдельно, если их исправление требует изменения согласованных решений.

### Распределение ответственности

| Участник | Ответственность |
|---|---|
| Пользователь | Согласование требований, принятие архитектурных решений, участие в анализе и ревью |
| ChatGPT | Обучение, проектирование, подготовка заданий, code review и анализ результатов |
| Codex | Реализация согласованных задач, проверки и работа с Git |

Codex не должен самостоятельно изменять согласованные бизнес-правила и принимать существенные архитектурные решения за пределами технического задания.

Подробные инструкции работы Codex определяются в `AGENTS.md` и соответствующих Skills.

## 8. Статусы задач

Основные статусы:

`Idea → Needs discussion → Ready → In progress → In review → Verification → Done`

| Статус | Значение |
|---|---|
| Idea | Идея, требующая дальнейшего рассмотрения |
| Needs discussion | Требуется обсуждение и согласование |
| Ready | Требования согласованы, задача готова к реализации |
| In progress | Задача находится в процессе реализации |
| In review | Выполняется code review |
| Verification | Выполняются необходимые проверки |
| Done | Выполнены все применимые критерии готовности |
| Deferred | Реализация отложена |
| Blocked | Реализация ограничена установленной проблемой |

Необходимо отдельно различать:

- **Реализовано** — соответствующий код существует.
- **Проверено статически** — выполнено code review.
- **Проверено исполнением** — успешно выполнены соответствующие тесты и проверки.
- **Не проверено** — отсутствует подтверждение корректности.
- **Завершено** — выполнены все применимые критерии Definition of Done.

Наличие кода, коммита или объединённого Pull Request само по себе не подтверждает корректность реализации.

## 9. Definition of Done

Задача считается завершённой при выполнении всех применимых критериев:

- Согласованные требования реализованы.
- Бизнес-правила и инварианты соблюдены.
- Реализация соответствует согласованной архитектуре.
- Не внесена необоснованная сложность.
- Существующее поведение не нарушено без согласования.
- Добавлены или актуализированы необходимые тесты.
- Применимые тесты успешно выполнены.
- Применимые статические проверки пройдены.
- Миграции проверены в безопасной среде, если они изменялись.
- Code review завершено.
- Критические замечания устранены.
- Документация актуализирована в рамках согласованного объёма задачи.
- Результат зафиксирован в Git.

Если отдельная проверка не выполнена, необходимо явно обозначить это и указать причину.

Завершение крупного этапа требует выполнения его собственных критериев готовности в дополнение к общему Definition of Done.

Основной приоритет проекта — понимание технических решений, корректность бизнес-логики и постепенное развитие инженерных навыков.
