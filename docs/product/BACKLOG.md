### 2.1. Q-030 — организация Monorepo

Основные направления:

- Размещение межсервисных контрактов в `contracts/`.
- Централизованное размещение инфраструктурных конфигураций в `infra/`.
- Разделение тестов сервисов и общесистемных тестов.
- Отдельное размещение будущего frontend.
- Сохранение Docker Compose на уровне корня репозитория.
- Сохранение самостоятельных конфигураций и зависимостей сервисов.
- Сохранение корневых и сервисных инструкций Codex.

Не создавать пустые директории под будущую функциональность.

Не внедрять Kafka, Kubernetes, Terraform, Ansible и frontend в рамках структурного рефакторинга.

Перемещение существующих контрактов не должно изменять их содержание или поведение API. Полноценная актуализация технической документации выполняется в Q-016.

### 2.2. Q-031 — структурный рефакторинг Demo Restaurant

Основные направления:

- Modular Monolith.
- Feature-first организация.
- Выделение бизнес-модулей `catalog` и `orders`.
- Размещение синхронизации внутри `catalog/sync`.
- Перенос ORM-моделей и репозиториев в модули-владельцы.
- Декомпозиция `DemoRestaurantService`.
- Сохранение `CatalogMutationService` внутри модуля каталога.
- Контролируемое межмодульное взаимодействие.
- Группированный Unit of Work.
- Ручной Dependency Injection.
- Управление ресурсами через lifespan.
- Централизованный HTTP-клиент.
- Feature-first организация тестов.
- Классификация тестов через pytest markers.

Необходимо сохранить:

- Существующие бизнес-правила.
- Full Snapshot Sync v3.
- Семантику `catalog_revision`.
- Транзакционные гарантии изменения каталога.
- Rollback-only.
- Идемпотентность обработки заказов.
- HTTP-контракты.
- Схему PostgreSQL и историю миграций.
- Существующее тестовое покрытие.

### 2.3. Q-032 — структурный рефакторинг Kitchen API

Основные направления:

- Modular Monolith.
- Feature-first организация.
- Выделение бизнес-модулей `catalog`, `cart`, `orders`, `checkout`, `users`, `auth`.
- Размещение синхронизации внутри `catalog/sync`.
- Перенос ORM-моделей, репозиториев, схем и роутеров в модули-владельцы.
- Выделение CheckoutService.
- Выделение операций управления пользователями.
- Интеграция ранее реализованных компонентов авторизации в новую архитектуру.
- Контролируемое межмодульное взаимодействие.
- Группированный Unit of Work.
- Ручной Dependency Injection.
- Управление ресурсами через lifespan.
- Переиспользование HTTPX AsyncClient в пределах процесса приложения.
- Централизованные HTTP-клиенты.
- Feature-first организация тестов.
- Классификация тестов через pytest markers.

В рамках структурного рефакторинга сохраняются существующие бизнес-операции и поведение системы.

Переработка доменной модели и исключение самостоятельных публичных репозиториев дочерних сущностей выполняются отдельными задачами Q-033–Q-035.

Новая функциональность авторизации, checkout и обработки заказов в рамках Q-032 не реализуется.

### 2.4. Q-033 — доменный рефакторинг Cart Aggregate

Состав агрегата:

- Cart — Aggregate Root.
- CartItem — дочерняя сущность.
- CartRepository — репозиторий агрегата.

Основные направления:

- Rich Domain Model на существующих SQLAlchemy-моделях.
- Предметные операции управления корзиной.
- Изменение дочерних сущностей через Cart.
- Защита существующих инвариантов корзины.
- Repository per Aggregate.
- Разделение ответственности между Application Service и Domain Model.
- Domain Services и Domain Policies при необходимости.
- Unit-тестирование доменных операций.
- Интеграционная проверка сохранения агрегата.

Конкретные методы, правила загрузки агрегата и границы конкурентных операций согласуются перед реализацией.

Новые бизнес-правила корзин, относящиеся к Q-011, не внедряются автоматически в рамках рефакторинга.

### 2.10. Общие ограничения архитектурного рефакторинга

В рамках Q-030–Q-038:

- Не изменять согласованные бизнес-требования без отдельного согласования.
- Не расширять функциональность приложения.
- Не изменять существующие HTTP-контракты.
- Не изменять схему PostgreSQL ради архитектурного перемещения кода.
- Сохранять историю миграций.
- Сохранять существующее тестовое покрытие.
- Не удалять и не ослаблять проверки для получения успешных результатов.
- Не создавать отдельные Domain Entities и дублирующие ORM Models.
- Не внедрять Imperative Mapping.
- Не вводить DI-фреймворки.
- Не создавать дополнительные микросервисы.
- Не внедрять Kafka и новую инфраструктуру без соответствующей задачи.
- Не перерабатывать существующие архитектурные диаграммы, CJM и документацию базы данных до Q-016.

Обнаруженные дефекты, требующие изменения согласованного поведения системы, фиксируются и обсуждаются отдельно.

Подробные архитектурные требования определяются в `REQUIREMENTS.md`.

Правила работы с техническим долгом:

- Не выполнять оптимизации без подтверждённой необходимости.
- Проблемы корректности данных и безопасности имеют приоритет над улучшениями производительности.
- Отличать подтверждённый дефект от потенциального риска и архитектурного компромисса.
- Не создавать отдельные задачи для проверок, уже входящих в согласованный объём существующих задач.
- Исправления не должны нарушать существующие бизнес-инварианты.
- Изменения схемы базы данных требуют отдельного согласования и проверки миграций.

## 8. Приоритеты

| Приоритет | Значение |
|---|---|
| P0 | Блокирует обязательную разработку, корректность данных, безопасность или необходимую верификацию |
| P1 | Необходимо для соответствующего запланированного этапа |
| P2 | Полезное улучшение, не блокирующее основные сценарии |
| P3 | Необязательное улучшение или эксперимент |

Высокий приоритет не означает необходимость немедленной реализации вне согласованной последовательности.

Задача с приоритетом P0 может быть отложена до завершения необходимых зависимостей.

## 9. Статусы задач и решений

| Статус | Значение |
|---|---|
| `Idea` | Потенциальное направление развития |
| `Needs discussion` | Требуется обсуждение и согласование |
| `Decided` | Решение согласовано |
| `Planned` | Задача включена в план реализации |
| `Ready` | Требования, техническое задание и критерии приёмки согласованы |
| `In progress` | Задача выполняется |
| `In review` | Выполняется code review |
| `Verification` | Выполняются необходимые проверки |
| `Done` | Выполнены все применимые критерии готовности |
| `Deferred` | Реализация отложена |
| `Blocked` | Реализация ограничена установленной проблемой |
| `Monitor` | Требуется наблюдение или измерение |
| `Ongoing` | Постоянная инженерная практика |
| `Optional` | Необязательное направление |
| `Out of scope` | Не входит в текущие границы проекта |
| `Promoted` | Идея переведена в самостоятельную задачу |

Основной жизненный цикл задачи:

`Idea → Needs discussion → Planned → Ready → In progress → In review → Verification → Done`

Не каждая задача обязана проходить все состояния.

При необходимости допускается возврат на предыдущий этап.

Статус задачи и её зависимости фиксируются отдельно.

Не использовать составные статусы наподобие `Planned after Auth` или `Planned with checkout`.

Частичная реализация, результаты проверок и причины приостановки указываются отдельно от основного статуса задачи.

Наличие кода, коммита или объединённого Pull Request само по себе не означает статус `Done`.

## 11. Правила ведения backlog

- Сохранять существующие идентификаторы задач и идей.
- Присваивать новым задачам уникальные идентификаторы.
- Разделять согласованные требования, задачи реализации и идеи.
- Указывать зависимости отдельно от статусов.
- Актуализировать состояние задач на основании подтверждённых результатов.
- Переносить завершённые задачи и согласованные закрытые вопросы в архив.
- Не удалять незавершённые задачи без согласования.
- Не дублировать подробно бизнес-правила из REQUIREMENTS.
- Не дублировать общий процесс разработки из ROADMAP и AGENTS.md.
- Согласовывать существенные изменения задач перед реализацией.
- Фиксировать результаты проверок и неустранённые ограничения.
- Не считать потенциальный риск подтверждённым дефектом без соответствующего анализа.
