# Avito-Kitchen — согласованные бизнес-требования

> **Статус:** Approved (бизнес-правила), редакция 2026-11-22.
> **Важно:** `Approved` означает, что правило согласовано, а не что оно реализовано или проверено. Фактическая реализация определяется кодом, миграциями и тестами в GitHub.
> **Область:** полный учебный план: согласованные правила backend, будущей Kafka-интеграции и расширений; оплата и доставка остаются вне первой версии. При расширении контрактов требования изменяются через обсуждение и ревью.

## 1. Назначение продукта и границы первой версии

Avito-Kitchen агрегирует каталоги нескольких ресторанов и их филиалов. Покупатель может просматривать каталог, регистрироваться, формировать отдельную корзину для каждого филиала, оформлять заказ и просматривать историю и статусы заказов.

**В первой версии Kitchen передаёт заказ системе Restaurant.** Restaurant принимает окончательное решение о принятии заказа и является источником истины по его бизнес-статусу. Собственная доставка, оплата, курьеры, возвраты и отмена заказов пока не реализуются. После завершения основы можно спроектировать отдельные сервисы оплаты и доставки.

Отдельная веб-панель ресторана не нужна. Для обучения межсервисной интеграции предусматривается защищённый административный API **Demo Restaurant**, позволяющий изменять тестовые данные через бизнес-сервисы, а не прямыми SQL-операциями.

## 2. Акторы, ответственность и источники истины

| Актор / компонент | Ответственность |
|---|---|
| Гость | Просматривает публичные рестораны, филиалы и меню без регистрации |
| Покупатель (`customer`) | Регистрируется, входит, управляет своими корзинами, оформляет заказы и смотрит свою историю |
| Администратор тестового Restaurant (`admin`) | Через защищённые API меняет филиалы, меню, цены, доступность и тестовые статусы заказов в пределах разрешений |
| Kitchen API | Публичный каталог (локальная копия данных), корзины, аутентификация покупателя, координация checkout, результаты и история заказов |
| Demo Restaurant | **Источник истины** о каталоге, ценах филиалов, доступности, приёме и бизнес-статусах заказов |
| Межсервисная интеграция | Обеспечивает аутентифицированную передачу данных и команд; протоколы уточняются по этапам |

Данные покупателя и его корзины принадлежат Kitchen. Исходные данные ресторана и бизнес-статусы заказа принадлежат Restaurant. Kitchen хранит синхронизированное представление данных ресторана.

## 3. BR-CAT — каталог, филиалы, цена и доступность

**BR-CAT-01.** У каждого ресторана есть одно **общее меню** с общими позициями `MenuItem` (название, описание, глобальная активность). У филиалов нет отдельных каталогов, но доступность позиций различается.

**BR-CAT-02.** Цена задаётся **для пары филиал + товар**, то есть на уровне `BranchMenuItem`, а не у общего `MenuItem`. Один и тот же товар может стоить по-разному в разных филиалах.

**BR-CAT-03.** `MenuItem.is_active` означает, что ресторан в принципе предлагает этот товар. `BranchMenuItem.is_available` означает, что позицию можно заказать в данном филиале прямо сейчас. Отсутствующая связь товар–филиал считается недоступностью.

**BR-CAT-04.** Заказ допустим, только если филиал активен, принимает заказы, товар активен и доступен в филиале. Цена для checkout берётся из состояния конкретного филиала; Restaurant повторно проверяет её при приёме заказа.

**BR-CAT-05.** Неактуальные или удалённые из текущего ассортимента сущности переводятся в неактивное состояние (*soft delete*) для сохранения ссылок и истории. Отсутствие сущности в **полном** snapshot означает деактивацию в Kitchen; отсутствие в **частичном** обновлении ничего не означает.

**BR-CAT-06.** Только Restaurant изменяет исходное состояние каталога. Kitchen не может произвольно редактировать синхронизированные цены, ассортимент или доступность.

**BR-CAT-07.** `BranchMenuItem.price` хранится в целых копейках (валюта первой версии — RUB). Для ещё не оценённого товара `price = NULL` допустима, но `is_available = true` допускается только при положительной установленной цене. При переносе модели нужно сохранить действующие цены из `MenuItem.price` в существующие связи филиал–товар; отсутствующие связи считаются недоступными. Изменение формата синхронизации требует повышения `schema_version`.

## 4. BR-SYNC — версии, полная и частичная синхронизация

**BR-SYNC-01.** Для каждого ресторана вводится **единая монотонная `catalog_revision`** для всего передаваемого состояния: общих товаров, филиалов, их цен и доступности. Изменение состояния и увеличение ревизии должны фиксироваться **одной транзакцией** Restaurant DB.

**BR-SYNC-02.** У нового согласованного состояния ревизия больше прежней. Снимок должен содержать ревизию именно того согласованного состояния, из которого прочитаны его данные. `generated_at` используется для диагностики/аудита, **не** для определения порядка данных.

**BR-SYNC-03.** Целевой контракт полного snapshot включает `snapshot_id` (идентичность конкретного снимка), `schema_version` (версия формата), `catalog_revision` и при необходимости `generated_at`. Независимые `branch_version` из текущей переходной реализации **удаляются при согласованной миграции**; до миграции они могут оставаться в коде. Не удалять поля из БД без отдельного ТЗ и проверки данных.

**BR-SYNC-04.** Полный snapshot заменяет представление каталога ресторана в Kitchen **атомарно**. Если его `catalog_revision` новее текущей, его можно принять **даже при пропуске нескольких ревизий**: он содержит полное состояние. Снимки с меньшей ревизией не перезаписывают более новые данные.

**BR-SYNC-05.** Частичное обновление (*delta*, будущий механизм) несёт только изменённые сущности и ревизию. Применяется, если его ревизия равна `current_revision + 1`; при пропуске нужна повторная доставка недостающих изменений либо **полный snapshot для восстановления**. Более старые изменения нельзя применять поверх новых.

**BR-SYNC-06.** Retry означает **повторную доставку той же логической операции** после сетевой ошибки или неизвестного результата. Повторно отправляемый snapshot сохраняет исходные `snapshot_id`, `catalog_revision` и содержимое. Если Restaurant перечитал БД и сформировал новый снимок, это новый `snapshot_id`.

**BR-SYNC-07.** Повторное получение того же snapshot не приводит к повторному применению. Необходима защита от конкурентных синхронизаций одного ресторана. Общая транзакция при применении snapshot обеспечивает rollback при ошибке.

**BR-SYNC-08.** Событийная передача частичных обновлений через Kafka планируется **после подтверждения рабочего HTTP baseline**. Конкретные Kafka topics, команды и события пока не утверждены.

**BR-SYNC-09.** Одна транзакция с фактическими изменениями каталога увеличивает `catalog_revision` ровно на 1 вне зависимости от числа изменённых строк. Транзакция без фактических изменений или с rollback ревизию не меняет. Restaurant хранит ревизию в отдельной таблице `catalog_state` (одна строка на ресторан), сериализует операции изменения каталога через блокировку строки `SELECT ... FOR UPDATE`, а затем изменяет каталог и ревизию в одной транзакции. Обычный уровень изоляции для записи — `READ COMMITTED` при соблюдении этого протокола.

**BR-SYNC-10.** Полный snapshot строится в читающей транзакции `REPEATABLE READ`: данные и `catalog_revision` берутся из одного согласованного состояния БД. Транзакция закрывается **до HTTP-отправки**. Все пути изменения синхронизируемых данных обязаны соблюдать BR-SYNC-09.

**BR-SYNC-11.** Restaurant не обязан сохранять полное содержимое snapshot в БД. Пока выполняется серия HTTP retry, повторно отправляется тот же сформированный payload с тем же `snapshot_id` и ревизией. Если после перезапуска исходный payload недоступен, Restaurant может построить новый полный snapshot с новым `snapshot_id`. Kitchen сохраняет текущую ревизию и данные для дедупликации обработанных снимков.

**BR-SYNC-12.** Kitchen хранит **SHA-256 контрольную сумму канонизированного бизнес-содержимого каталога** для последнего принятого состояния. Из расчёта исключаются транспортные и служебные поля (`snapshot_id`, `generated_at`, сведения о попытке доставки и т. п.); включаются все поля, влияющие на смысл каталога, включая цены в копейках, активность и доступность. Канонизация должна задавать детерминированный порядок филиалов, товаров и связей, стабильное представление чисел и сериализацию полей; точный формат закрепляется в контракте и тестовых векторах перед реализацией. При повторном полном snapshot с той же `catalog_revision` и той же контрольной суммой повторного применения нет. **Та же ревизия с другой суммой — нарушение инварианта**: нельзя молча перезаписывать состояние, требуется диагностическое событие/ошибка и расследование. SHA-256 используется для выявления расхождений, но не заменяет аутентификацию источника.

**BR-SYNC-13.** Kitchen хранит историю обработанных `snapshot_id` и привязанных к ним ревизий/контрольных сумм **30 дней**, с безопасной периодической очисткой истёкших записей. **Текущие `catalog_revision` и контрольная сумма актуального состояния хранятся постоянно**, независимо от очистки истории. После очистки старый snapshot всё равно отклоняется по устаревшей ревизии; повтор с той же текущей ревизией не применяет данные повторно. Необходимо определить устойчивость к `snapshot_id` с другим payload при ещё существующей записи.

**BR-SYNC-14.** Для будущей Kafka-интеграции **одна успешная транзакция изменения каталога соответствует одному логическому delta-событию** с новой `catalog_revision`. Событие может описывать изменения нескольких сущностей. Транзакция без фактических изменений не создаёт новую ревизию и delta-событие. Запись в Transactional Outbox должна атомарно сопровождать изменение каталога и инкремент ревизии. Обработчик Kitchen применяет delta **только** при `incoming_revision = current_revision + 1`.

**BR-SYNC-15.** Если delta пришла с пропуском ревизии, Kitchen не применяет ни её, ни следующие delta поверх неполного состояния. Система должна инициировать восстановление актуального состояния через полный snapshot; после успешного восстановления можно продолжить обработку более новых событий. Полный snapshot **допускает пропуск** ревизий и заменяет всё представление атомарно. Повторные события дедуплицируются по `event_id` и проверяются по ревизии; события со старой ревизией не откатывают состояние.

**Открытые детали реализации (не бизнес-вопросы):** точная схема таблиц, формат канонизации и тестовых векторов, HTTP-контракты и алгоритм очистки; на этапе Kafka — названия топиков, ключи партиционирования, структура сообщений и управление отложенными событиями. Эти детали согласуем при подготовке соответствующих задач Codex.

## 5. BR-CART — корзина

**BR-CART-01.** У авторизованного покупателя может быть **несколько корзин**, но не более одной корзины на пару «покупатель + филиал». Одна корзина не содержит товары из разных филиалов.

**BR-CART-02.** Гость может просматривать каталог; управление корзиной, checkout и история заказов доступны после аутентификации.

**BR-CART-03.** При изменении цены Kitchen обновляет представление корзины, показывает пользователю, что именно изменилось (старая и новая цена), и требует подтверждения новых условий **до повторной попытки оформления**. Незаметно оформить заказ по другой цене нельзя.

**BR-CART-04.** Если товар стал неактивным или недоступным, оформление блокируется до исправления корзины. Покупателю показывается конкретная причина.

**BR-CART-05.** Конкурентные изменения количества или создание корзины не должны приводить к потерянным обновлениям и дублированию корзин. Изменение корзины выполняется под транзакционной блокировкой `SELECT ... FOR UPDATE`; уникальность пары `(customer_id, branch_id)` защищается ограничением БД и корректной обработкой конкурентного создания. У корзины есть `cart_version`, возрастающая при изменении состава/количества. Клиент передаёт ожидаемую версию для модификации; при устаревшей версии Kitchen отвечает конфликтом (например, HTTP 409) и возвращает возможность получить актуальную корзину.

**BR-CART-06.** После принятия заказа Restaurant корзина очищается. При окончательном отказе корзина сохраняется для исправления. При timeout/неопределённом результате корзина сохраняется, а повторное создание **другого** заказа из той же корзины блокируется до выяснения результата. Повтор с исходным `order_id` разрешается как восстановление существующей попытки.

**BR-CART-07.** На время заказа со статусом `pending` выбирается **вариант A**: изменение состава и количества соответствующей корзины логически заблокировано до выяснения результата. Это состояние сохраняется в БД и не реализуется удержанием PostgreSQL-блокировки на время сетевого запроса. После принятия заказа корзина очищается, после окончательного отказа — разблокируется с сохранением товаров. При неизвестном результате остаётся заблокированной для новой попытки, но разрешено восстановление по прежнему `order_id` с тем же содержимым.

**Отложенная альтернатива:** разрешить редактировать корзину во время `pending` и после принятия удалять только позиции/количества, зафиксированные в заказе. В первую версию **не входит**; см. `IDEA-016` в BACKLOG.

**BR-CART-08.** Для каждой позиции корзины Kitchen хранит `accepted_unit_price` — цену в копейках, последнюю подтверждённую пользователем. При любом изменении цены (увеличении или уменьшении) Kitchen сообщает прежнюю и актуальную цену и требует явного подтверждения. Подтверждение обновляет `accepted_unit_price` и `cart_version` в одной транзакции, с проверкой ожидаемой версии корзины. При checkout Kitchen повторно сверяет подтверждённую цену с актуальной ценой конкретного филиала; при новом расхождении оформление прекращается до повторного согласия. Restaurant независимо проверяет фактическую цену при приёме заказа. Формат HTTP API подтверждения цены определяется при проектировании соответствующего блока.

## 6. BR-ORDER — оформление, отказы и жизненный цикл

**BR-ORDER-01.** При нажатии «Оформить» Kitchen инициирует логическую попытку заказа (`order_id`) и фиксирует состояние ожидания; Restaurant принимает окончательное решение. Клиент может видеть «заказ обрабатывается» (`pending`), но сообщение об **успешном оформлении** получает только после принятия заказа рестораном. Это правило сохраняется и при будущей асинхронной Kafka-интеграции.

**BR-ORDER-02.** Restaurant проверяет филиал, доступность, активность товаров, цены и остальные бизнес-ограничения на момент приёма. Он сохраняет **все окончательные бизнес-отказы** с причиной и связью с `order_id`.

**BR-ORDER-03.** Идемпотентность: повтор того же `order_id` с тем же запросом возвращает сохранённый результат; тот же `order_id` с другим содержимым приводит к конфликту. Новый осмысленный заказ после отказа получает новый `order_id`.

**BR-ORDER-04.** При потере HTTP-ответа/timeout нельзя предполагать, что заказ не был принят. Kitchen хранит восстанавливаемое состояние `pending` и повторяет исходную операцию с тем же идентификатором и содержимым; запрещено создавать второй заказ до разрешения неопределённости.

**BR-ORDER-05.** Для истории заказа сохраняется снимок названия, количества и цены позиции на момент оформления. Последующие изменения каталога не меняют историю принятого заказа.

**BR-ORDER-06.** Покупатель видит только свои заказы и их историю. Restaurant — источник истины по бизнес-статусам, Kitchen отражает согласованное состояние.

**BR-ORDER-07.** `pending` — состояние Kitchen, ожидающей достоверное решение Restaurant. Restaurant при первоначальной обработке переводит заказ в `accepted` либо `rejected`. Далее допустимы **только** последовательные бизнес-переходы `accepted → preparing → ready → completed`; `rejected` и `completed` — терминальные состояния. Перескакивание этапов и возвращение назад запрещены (`409 Conflict`). Повторное указание уже установленного статуса допускается как идемпотентное действие без повторной записи перехода. Отмена в первой версии отсутствует. Restaurant — источник истины по бизнес-статусам.

**BR-ORDER-08.** Отмена заказов в текущем scope не поддерживается. Позднее, с оплатой, правила отмены будут спроектированы отдельно.

**BR-ORDER-09.** После timeout или потери ответа Kitchen **автоматически восстанавливает `pending`-заказ** через отдельный Python-worker с состоянием повторных попыток в PostgreSQL, независимо от того, открыт ли браузер. Worker повторяет **исходный, неизменный** запрос с тем же `order_id` и составом заказа, используя интервалы с увеличивающейся задержкой (*exponential backoff*). Одновременная обработка одной попытки несколькими экземплярами worker должна быть исключена; долгие сетевые операции не должны удерживать транзакционную блокировку PostgreSQL.

**BR-ORDER-10.** После первой неудачной попытки HTTP-взаимодействия разрешены **семь автоматических повторных попыток** с базовыми интервалами 5 секунд, 15 секунд, 45 секунд, 2 минуты, 5 минут, 15 минут и 30 минут; применяется небольшой случайный разброс (*jitter*). При исчерпании попыток запись восстановления переводится в техническое состояние `needs_attention`. Это **не означает отказ Restaurant**: бизнес-статус заказа остаётся `pending`, покупателю показывается «Уточняем статус заказа», а корзина остаётся заблокированной для изменений и создания нового заказа. Исходный `order_id` и payload должны оставаться неизменными.

**BR-ORDER-11.** Бизнес-статус заказа и техническое состояние восстановления хранятся раздельно. Для восстановления предусмотрены состояния `scheduled` (ожидает выполнения), `leased` (зарезервировано worker), `needs_attention` (исчерпаны автоматические попытки) и `completed` (восстановление завершено); сохраняются как минимум счётчик попыток, `next_retry_at` и срок действия lease. Полная схема и имена полей уточняются при реализации без изменения бизнес-семантики.

**BR-ORDER-12.** Несколько экземпляров worker выбирают задания с помощью PostgreSQL `FOR UPDATE SKIP LOCKED` и временной аренды задачи (*lease*), не удерживая открытую транзакцию при HTTP-вызове. После истечения lease невыполненная попытка может быть безопасно возобновлена. Повторная доставка допускается, поэтому операции обязаны быть идемпотентными.

**BR-ORDER-13.** Через защищённый Admin API разрешён ручной повторный запуск восстановления для `needs_attention`, но запрещено вручную выставлять `accepted` или `rejected` без достоверного решения Restaurant. Возобновление использует прежние `order_id` и исходный payload; в истории фиксируются попытки и причины ошибок без утечки секретов.

**BR-ORDER-14.** У заказа Restaurant есть собственная монотонная `status_version`, не связанная с `catalog_revision`. При первоначальном сохранении окончательного решения Restaurant фиксирует соответствующий бизнес-статус и исходную версию; каждый реальный успешный переход статуса увеличивает `status_version` ровно на единицу. Конкурентные изменения проверяют ожидаемую версию и выполняются атомарно. Повтор того же статуса не увеличивает версию.

**BR-ORDER-15.** Restaurant сохраняет историю переходов статуса: прежний и новый статус, момент изменения, идентификатор инициатора и версию. Данные должны позволять проверить, кем и в каком порядке выполнялись переходы, без раскрытия секретов. Изменять тестовые статусы вправе только авторизованный администратор через Restaurant Admin API и предметный сервис.

**BR-ORDER-16.** Kitchen хранит локальное представление статуса и `status_version` Restaurant для отображения покупателю. Оно не может откатываться на более старую версию из-за задержки доставки. До Kafka Restaurant **инициирует HTTP Webhook** при изменении статуса; периодический polling всех заказов не используется.

**BR-ORDER-17.** Restaurant сохраняет изменение статуса, увеличение `status_version`, историю перехода и запись **Transactional Outbox** в одной транзакции PostgreSQL. Отдельный worker доставляет уведомление в защищённый внутренний API Kitchen через HTTP; при недоступности Kitchen запись остаётся для повторной доставки. Запрос HTTP выполняется без удержания транзакции изменения бизнес-данных.

**BR-ORDER-18.** Webhook содержит как минимум `event_id`, идентификатор ресторана и заказа, новый статус, `status_version` и время события. Kitchen проверяет идентичность сервиса-отправителя, соответствие заказа ресторану, допустимость данных и порядок версий. Повторные `event_id` обрабатываются идемпотентно; более старая версия не перезаписывает новую. Успешный HTTP-ответ означает, что обновление зафиксировано в Kitchen DB. Гарантия доставки — **at least once**, а не exactly once.

**BR-ORDER-19.** При временной недоступности Kitchen допускаются повторные отправки webhook с backoff и jitter. Должен быть предусмотрен защищённый способ адресной сверки статуса с Restaurant после длительного сбоя или обнаруженного расхождения; эта сверка не является регулярным polling всех заказов. При переходе на Kafka используется тот же бизнес-смысл события и версия, но меняется транспорт; конкретные форматы API/Outbox согласуются в техническом задании.

## 7. BR-IDENTITY — регистрация, доступ и безопасность

**BR-IDENTITY-01.** Покупатель регистрируется с уникальным нормализованным email и паролем. В PostgreSQL хранится только безопасный хеш пароля **Argon2id**, а не исходный пароль. Публичная регистрация создаёт только роль `customer`; самоназначение `admin` запрещено.

**BR-IDENTITY-02.** Для авторизации используются **JWT access token** со сроком жизни **15 минут** и **непрозрачный криптографически случайный refresh token** со сроком жизни **14 дней**. Непрозрачный refresh token не является JWT. В БД хранятся только хеши refresh-токенов и записи пользовательских сессий.

**BR-IDENTITY-03.** При успешном обновлении токенов применяется **refresh-token rotation**: старый refresh token становится недействительным, выдаётся новый. Повторное использование уже заменённого токена считается подозрительным и приводит к отзыву связанной сессии/семейства токенов. Корректное поведение при параллельных refresh-запросах и конкурентных повторах определяется и тестируется до реализации.

**BR-IDENTITY-04.** Один пользователь может иметь несколько сессий для разных устройств. Поддерживаются logout текущей сессии и logout all. При завершении сессии refresh token отзывается. Уже выданный access JWT может оставаться действительным до срока истечения, если не выбран отдельный механизм немедленного отзыва; этот компромисс должен быть явно обозначен в API и тестах.

**BR-IDENTITY-05.** Для браузера refresh token передаётся через `HttpOnly`, `Secure` cookie с подходящей настройкой `SameSite`; access token хранится в памяти веб-приложения. Cookie-authenticated операции должны иметь защиту от CSRF, а API — корректную конфигурацию CORS. Конкретная модель защиты уточняется при проектировании веб-интеграции.

**BR-IDENTITY-06.** Регистрация требует обязательного **подтверждения email перед первым входом**. Новый аккаунт получает состояние `email_unverified`. Email подтверждается по одноразовому случайному токену со сроком **24 часа**, хеш которого хранится на сервере. Неподтверждённый пользователь может запросить повторное письмо с ограничением частоты запросов, но не может получать полноценные пользовательские сессии и оформлять заказы.

**BR-IDENTITY-07.** Восстановление пароля выполняется по одноразовому случайному токену со сроком **30 минут**; хранится только его хеш. После успешной смены пароля отзываются все refresh-сессии и отправляется уведомление. Ответ на запрос восстановления не должен раскрывать, существует ли email в системе; необходим rate limiting.

**BR-IDENTITY-08.** При локальной разработке почтовые сообщения регистрации и восстановления отправляются на тестовый SMTP-сервер **Mailpit**; подключение реального почтового провайдера — отдельная задача.

**BR-IDENTITY-09.** Пользовательские роли первой версии: `customer` и `admin`. Роль `customer` даёт доступ только к собственным корзинам, заказам и сессиям. Роль `admin` предназначена для тестового управления Restaurant; её выдача возможна только доверенной административной процедурой, не через публичный API регистрации. Администратор не получает автоматически доступ к чужим пользовательским данным и секретам.

**BR-IDENTITY-10.** Публичные рестораны, филиалы и каталог доступны без авторизации. Для работы с корзиной, checkout и историей заказов обязательна пользовательская сессия. На каждом запросе проверяются аутентификация, права на операцию и **владение конкретным ресурсом**. Нельзя доверять подставленному пользователем идентификатору или неподписанному заголовку как доказательству личности.

**BR-IDENTITY-11.** Административные операции изменения каталога, филиалов, цен, доступности и тестовых статусов заказов реализуются как защищённый **Restaurant Admin API** без отдельной веб-панели. API вызывает предметные сервисы, соблюдает бизнес-инварианты и увеличивает `catalog_revision` при изменении каталога. Публичные endpoints произвольного SQL запрещены.

**BR-IDENTITY-12.** Пользователи и роли хранятся в **Kitchen**; Demo Restaurant не реализует отдельную регистрацию администраторов. Для административных операций Kitchen выпускает асимметрично подписанный JWT (предварительный алгоритм — **RS256**) с отдельным `audience` и требуемыми правами. Restaurant проверяет подпись по публичному ключу, `issuer`, `audience`, срок действия и полномочия. Kitchen хранит приватный ключ; Restaurant не должен иметь к нему доступ.

**BR-IDENTITY-13.** Межсервисные запросы Kitchen ↔ Restaurant аутентифицируются через **отдельные сервисные идентичности/credentials**. Пользовательский JWT и роль `customer` не подходят для межсервисных команд и синхронизации. Нельзя доверять `restaurant_external_id` из тела запроса без проверки полномочий отправителя.

**BR-IDENTITY-14.** Применяются принципы **deny by default** и **least privilege**: отсутствие разрешения означает отказ. Проверка только роли без проверки владельца ресурса недостаточна. Секреты и чувствительные токены запрещено хранить в Git и выводить в журналы.

**BR-IDENTITY-15.** Операции администратора должны журналироваться с идентичностью исполнителя, временем и безопасными сведениями о том, какие данные изменены. Журнал аудита не должен содержать секреты или чувствительные токены.

**BR-IDENTITY-16.** При тестировании обязательны негативные проверки: доступ к чужим корзинам/заказам, запрет изменения каталога обычным пользователем, истёкшие JWT, неверные `issuer`/`audience`, отсутствующая авторизация и повторное использование refresh token.

**Открытые детали реализации:** конкретные API endpoints, формат выдачи и обновления ключей, способ доставки ключа Restaurant, механизм rate limiting/CSRF, точная схема таблиц и процедур администрирования. Они определяются перед соответствующими задачами Codex, а не произвольно агентом.

## 8. BR-KAFKA — согласованные правила будущей событийной интеграции

> **Статус:** архитектурные правила утверждены, Kafka **не внедрена**. Полноценный проверенный HTTP baseline — обязательная точка отсчёта. Конкретные топики, схемы, ключи и библиотека определяются перед этапом Kafka.

**BR-KAFKA-01.** Первые потоки для перевода на Kafka — **изменения каталога** и **события статусов заказов**. После их реализации и проверки рассматривается перевод **команд создания заказов** на Kafka. Публичный REST API между браузером и Kitchen остаётся HTTP; не нужно переводить чтение каталога на Kafka.

**BR-KAFKA-02.** Изменения каталога отправляются как delta-события в соответствии с BR-SYNC-14–15. Одной транзакции изменений каталога соответствует **одно логическое delta-событие**, даже если внутри транзакции изменилось несколько объектов.

**BR-KAFKA-03.** Отправка сообщений из Restaurant не должна терять уже зафиксированные изменения: используем **Transactional Outbox**. Принимающая сторона фиксирует идемпотентность обработки (`event_id`, Inbox/уникальное ограничение и версии) в одной БД-транзакции с изменением своего состояния. Повторная доставка допустима (*at least once*); сквозная *exactly once* не предполагается.

**BR-KAFKA-04.** Для статусов заказов сохраняем `status_version` и авторитет Restaurant. Kitchen обрабатывает событие, если оно новее локального состояния, и не откатывает уже применённую более новую версию. История переходов Restaurant сохраняется независимо от способа доставки.

**BR-KAFKA-05.** При будущей асинхронной команде создания заказа Kitchen сохраняет `pending` и неизменяемые `order_id`/payload, а клиент получает окончательное решение только после подтверждения Restaurant. Повтор команды не создаёт второй заказ, а отсутствие ответа не означает `rejected`.

**BR-KAFKA-06.** Временные ошибки доставки/обработки повторяются с backoff и контролем числа/частоты попыток. Неисправимые сообщения помещаются в **DLQ (dead-letter queue)** для анализа и контролируемого повторного запуска. Попадание события каталога в DLQ **не разрешает молча применять более поздние delta с пропуском**; требуется восстановление полного состояния или корректная повторная обработка. Отметка обработки сообщения, состояние БД и порядок по ключу должны быть согласованы.

**BR-KAFKA-07.** Для диагностики сообщений предусматриваются идентификаторы события и корреляции, наблюдаемость ошибок потребителей, lag, количество повторов и DLQ. Контракты событий документируются (например, AsyncAPI), поддерживается версионирование схем. Конкретные инструменты и метрики выбираются при внедрении.

## 10. Приёмка и статус требований

Для каждого блока применять последовательность: **бизнес-правила → сценарии/ошибки → БД и ограничения → Repository/UoW → Service → API/контракты → тесты → ревью → Docker-верификация**. Наличие кода само по себе не означает выполнение требования.

Статусы: `Approved` — согласовано; `Implemented` — код существует; `Verified` — применимые проверки выполнены; `Done` — принят результат и выполнен DoD. В `BACKLOG.md` живут идеи и пока не решённые вопросы, а не обязательные требования.
